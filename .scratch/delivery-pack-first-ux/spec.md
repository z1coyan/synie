# 销售发货：装箱清单 Tab 拆分与「从装箱清单获取」（delivery-pack-first-ux）规格

Status: resolved

经 `/grill-with-docs` 逐问定案（2026-07-29）。术语沿用根 `CONTEXT.md` 既有词条（**装箱清单（行）**、**发货条目**、**已发数量**、**发货超发比例**），本次无新词条、无领域语义变更；不立 ADR——纯前端录入体验优化，全部取舍可逆，领域规则（装箱可选、审核全有或全无）一字未动。

## Problem Statement

- 发货抽屉是一条纵向长表单：头字段 → 发货条目 → 装箱清单 → 借贷科目。装箱清单是可选子表（多数发货不需要箱单），却恒占一屏高度，不需要箱单的用户每次都要滚过它。
- 装箱行物料候选 = 本单发货条目去重物料，条目为空时装箱表格禁止加行——**依赖方向锁死为「先条目后装箱」**。而仓库现场的真实动线常常是反的：货先装箱（箱单是物理事实），单证后补。当前系统不支持这条「先装箱、后补条目」的路径，用户只能线下记箱单、再回系统逐行点订单条目，重复劳动且易错。

## Solution

- **Tab 拆分**：抽屉内容切两 tab——「发货信息」（头字段＋发货条目＋借贷科目，默认 tab）与「装箱清单」（装箱行表格独占，标签带行数徽标）。查看/编辑/新建三模式同构。
- **依赖方向反转**：装箱行物料候选改为「可发货订单条目池」（同公司同对手、订单已审核、未发数量 > 0——与现有订单条目弹窗同一口径）去重物料；装箱表格可加行条件从「先有发货条目」放宽为「选齐公司与对手」。
- **「从装箱清单获取」按钮**：发货条目工具栏新动作，按物料汇总装箱量（折默认单位），在条目池内 FIFO 自动分摊生成缺失物料的发货草稿行；已有条目的物料一律不动；结果按干净/有料分两档反馈（sonner / 弹框三组）。
- 全部是草稿期录入加速：生成行就是普通草稿行（可改可删），保存走既有 `persistItems` 链路，审核走既有全部校验。后端零改动。

## User Stories

1. 作为销售内勤，我希望发货抽屉按「发货信息 / 装箱清单」分 tab，以便不需要箱单时不被装箱区占屏。
2. 作为销售内勤，我希望装箱 tab 标签上能看到行数，以便不点开就知道这票有没有箱单。
3. 作为仓管，我希望还没建发货条目时就能录装箱行（物料从可发货订单条目池选），以便按现场「先装箱」的真实顺序作业。
4. 作为仓管，我希望录完装箱后一键让系统按装箱量生成发货条目，以免逐行手点订单条目的重复劳动。
5. 作为仓管，我希望一个物料的装箱量按订单日期从早到晚自动分摊到多张订单的条目上（FIFO），装满一条扣下一条，以免我手工拆量。
6. 作为仓管，我希望已有发货条目的物料不被按钮触碰，以便我手工调过的行不被覆盖。
7. 作为仓管，我希望装箱量超过全部候选条目未发总量时，系统只足额分配、把尾差明确报给我，而不是悄悄丢掉或硬压进某条订单——怎么处理尾差是我的业务决定。
8. 作为仓管，我希望某物料有零候选、或候选订单币种与本单不一致时被明确告知，以便我换发货单或找商务处理，而不是保存/审核时吃莫名报错。
9. 作为仓管，我希望生成行自动带上头默认仓库、数量折算分毫不差（审核的装箱等式不被破坏），以便生成即可保存、保存即可审核。
10. 作为仓管，我希望头默认仓库为空时按钮直接拦我（提示先填默认仓），而不是产出一批保存必挂的无仓行。
11. 作为销售内勤，我希望按钮跑完有清晰的结果反馈：全顺利一句话提示；有尾差/零候选/币种不符/既有行对不上时弹框点名，以便审核前我能逐项处理。
12. 作为销售内勤，我希望公司/对手变更时条目与装箱行仍一并清空（现状保留），以便两 tab 数据始终与头一致。

## Implementation Decisions

以下均为已定案口径（`/grill-with-docs` 产物）：

- **Tab 结构**：「发货信息」＝头字段＋发货条目表格＋借贷科目（保持现有相对位置与校验，借贷科目不单独成 tab）；「装箱清单」＝装箱行表格独占，标签带行数徽标（如 `装箱清单 (3)`）。三模式（查看/编辑/新建）同构。落点：`web/app/routes/_app/scm/sales-deliveries/-delivery-drawer.tsx`。
- **物料候选来源反转**：装箱行物料候选＝可发货订单条目池去重物料，池口径与现有 `orderItemGridFilter` 完全一致（同公司、同对手、订单已审核、`remainingBaseQty > 0`）；`canCreate` 条件从 `headerReady && materialOptions.length > 0` 放宽为 `headerReady`（候选为空时下拉给空态提示即可）。「条目清空则装箱行一并清空」的 `resetItems` 联动**保留**（头变池变，两行都作废重来）。
- **按钮语义（A，增量补齐）**：「从装箱清单获取」只处理**还没有任何发货条目**的物料；已有条目的物料一律不动（无论数量是否对得上，对不上只进结果提醒）。
- **匹配规则（b，FIFO 分摊）**：按物料把装箱行汇总为默认单位量；该物料候选条目池按订单日期升序（同单按行 `idx` 升序，再按条目 id 兜底，保证确定性）依次扣 `remainingBaseQty`，装满一条扣下一条，一物料可拆多行。
- **尾差（只分不超）**：装箱汇总超出全部候选未发合计时，只足额分配，余量**不**压进末行（用户拍板，否决了「压进末行交给超发容差」的方案——尾差如何处理是业务决定，系统不猜），报进结果反馈由用户手工补行或改装箱。
- **币种锁定**：发货单要求全部行订单原币一致（既有领域规则）。生成时：已有条目则以现有行币种锁候选池；空条目则以本次所涉全部候选中订单日期最早者的币种定整单币种；异币种候选整批排除并进结果反馈。
- **生成行字段**：订单条目＝FIFO 命中条目；单位随订单条目锁定带出；**数量＝分摊 base × 该单位换算系数的精确值**（`qty` 列无精度限制，服务端 `base = qty ÷ factor` 6 位重算恰好回到分摊 base，审核装箱等式分毫不差）；仓库统一预填头默认仓；其余快照字段走既有 `transformItem` 缓存链路。生成即普通草稿行，可改可删。
- **头仓拦截**：头默认仓库为空时点按钮即 toast 拦截（「请先填写默认仓库」），一行不生成——否决了「照常生成留空仓、保存报错驱动」的方案（批量动作应产出可直接保存的草稿）。
- **结果反馈两档**：全干净 → sonner 一句「已从装箱清单生成 N 行发货条目」；有任何注意项 → 弹框三组列明：①已生成（物料→订单→数量，拆行逐列）②未分配（尾差：装箱 X/已分 Y/余 Z；零候选；币种不符——审核前必须人工处理）③对不上但未改动（已有条目合计 ≠ 装箱汇总，仅提醒不动数据）。
- **纯前端**：池查询（`salOrderItems` 带 `remainingBaseQty` 过滤）与单位换算（`materialUnitClient`，`LiveBaseQtyField` 先例）前端都拿得到；FIFO 分摊抽为纯函数；生成行写入本地 `items` state 后由既有 `persistItems` 落库。后端、领域模型、权限、打印目录零改动。
- **文档**：交付时同步 `docs/产品文档/销售发货.md`（tab 结构、物料候选口径变化、按钮路径与 FIFO/尾差/币种规则）；核对 `CONTEXT.md` 装箱词条（预计无需变更——领域语义未动）。

## Testing Decisions

- **唯一新接缝：FIFO 分摊纯函数**——输入（装箱汇总 per 物料、候选条目池、既有行、锁定币种、头仓）→ 输出（生成行、未分配清单、提醒清单），不碰 React/网络，用 `bun test` colocated 单测覆盖（prior art：`web/app/lib/amount.test.ts`）。
- 好测试的标准：每个用例只断言「给定输入，生成的行集合与报告内容是什么」，不测 React 组件内部状态。
- 测试重点：
  - FIFO 顺序：跨订单按日期升序扣量、装满再扣下一条、同单按行序。
  - 尾差：超剩余只足额分配，余量进未分配报告、不压末行。
  - 币种：已有行锁币 / 空行最早候选定币 / 异币种排除进报告。
  - 增量：已有条目的物料整物料跳过、对不上进提醒组。
  - 折算：转换单位下生成行 `qty = base × factor` 精确回算（6 位 base 无损）。
  - 零候选进报告；空装箱输入不生成不报错。
- 抽屉交互（tab 切换、按钮禁用态、弹框呈现）以手工验证为准，不新设组件测试接缝；后端无改动故无服务端测试。

## Out of Scope

- 匹配歧义时弹窗让用户逐物料手挑（ grilling 时已否决，手工路径＝现有订单条目弹窗）。
- 「全量重建」或「只回填数量」的按钮变体（已否决，A 语义唯一）。
- 尾差自动压末行（已否决）——将来若业务确认「尾差即超发」可再加开关，属领域规则变更，另行定案。
- 装箱行箱级属性（毛重/尺寸）、装箱清单自身任何领域语义变更；采购入库侧镜像（采购无装箱概念）。
- 后端 API、权限、打印模板目录的任何改动。

## Further Notes

- 本规格与 `.scratch/delivery-pack-list/`（装箱清单本体）是配套关系：那期建了「可选子表＋审核全等校验」，本期让这条子表在 UX 上成为可选的**录入起点**。
- 生成行的并发风险（生成到审核间订单被他人发完/关闭）由既有保存/审核校验兜底，不另做锁。
