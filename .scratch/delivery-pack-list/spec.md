# 销售发货装箱清单（delivery-pack-list）规格

Status: resolved

经 `/grill-with-docs` 逐问定案（2026-07-27）。术语唯一定义在根 `CONTEXT.md`（**装箱清单（行）**、**装箱单**两词条，已随定案预先写入）；本功能不写 ADR——纯增量子表，两个关键取舍（扁平 vs 两层、= vs ⊆）均可向后兼容演进，不满足「难以逆转」。

## Problem Statement

- 销售发货单目前只有发货条目（金额/订单勾稽层），没有实物装箱事实的记录处：随货给客户的箱单（哪箱装了什么、装了多少）系统录不了，只能线下 Excel 维持。
- 装箱与单证脱节，审核人无法在系统内核对「装箱数量与发货数量一致」，错装、漏装、多装要到客户收货时才暴露。

## Solution

- 发货单下加可选子表**装箱清单**：扁平装箱行（箱号＋物料＋单位＋数量＋行备注），箱号是行上的分组列——一箱多物料、一物料拆多箱都落在行模型上，不建箱头实体。
- **全有或全无**：整表可不填（照常审核）；填了则审核时按物料汇总硬校验「Σ 装箱行 base ＝ Σ 该物料全部发货条目 base」逐物料相等，草稿不卡、审核硬拦。
- 纯实物复核层：不落库存/总账/投影、无账面后果；权限随 `sales.delivery` 不新增权限码；作为发货单 has_many 循环区自动进入打印模板字段目录，箱单走既有模板打印体系输出。

## User Stories

1. 作为仓管/销售内勤，我希望在发货单草稿上录入装箱行（箱号＋物料＋数量），以便把随货箱单事实留在系统里。
2. 作为仓管，我希望一个箱号可以写多行（不同物料），以便还原「一箱装多物料」的装箱常态。
3. 作为仓管，我希望同一物料可以拆到多个箱号，以便反映一物料分多箱的尾数装箱。
4. 作为仓管，我希望装箱行单位可用物料默认单位或转换单位、系统自动折算 base，以便按装箱现场的实际计量录入。
5. 作为仓管，我希望箱号必填（自由文本），以便每行都有箱归属——本公司发货全部装箱，无散件语义。
6. 作为销售内勤，我希望装箱行保存时冻结物料快照（编号/名称/规格/客户料号/单位名），以便箱单口径不因主数据后改而变。
7. 作为销售内勤，我希望装箱清单整表可以不填，以便不需要箱单的发货单照常录入审核。
8. 作为审核人，我希望填了装箱清单的发货单在审核时被强制核对「逐物料装箱量＝发货量」，不一致即拒审，以便错装漏装在发货前暴露。
9. 作为审核人，我希望装箱行里出现发货单没有的物料同样拒审，以便多装错装被拦住。
10. 作为仓管，我希望草稿阶段不被校验打扰，以便边装箱边补录、装齐后一次审核（同容差校验先例）。
11. 作为销售内勤，我希望装箱行随发货单锁死/级联删除，以便生命周期不需要第二套规则。
12. 作为销售内勤，我希望打印模板里能用装箱循环区输出箱单，以便按公司版式打印随货文件。
13. 作为系统管理员，我希望装箱清单不新增权限码、随销售发货授权，以便岗位授权矩阵不膨胀。

## Implementation Decisions

以下均为已定案口径（`/grill-with-docs` 产物）：

- **子表结构**：`sal_delivery_pack_line` 挂**发货单**（不挂发货条目），行＝箱号＋物料＋单位＋数量＋`base_qty`＋行备注；箱号必填自由文本（分组/排序按文本精确匹配）；数量 > 0；单位限该物料默认单位或转换单位，系统折算 `base_qty`（6 位，同既有行模型先例）。
- **物料快照**：行保存冻结文本五字段（编号/名称/规格/客户料号/单位名），口径同发货条目但**不复制图纸挂接**。
- **审核校验（全有或全无）**：发货单审核时，存在装箱行则按物料分组比对两集合（默认单位口径）完全相等——漏装任一物料、任一物料不等、含发货外物料，均拒审并点名物料与两侧数量；无装箱行则跳过校验。草稿保存不校验（同超发/超收容差先例）。
- **不挂发货条目**：装箱行只是同单内的物料＋数量行，与发货条目无引用——实物复核层与金额/订单勾稽层解耦（同一物料多发货行时装箱现场无从也无需区分条目归属）。
- **生命周期**：随单级联删除、审核后随单锁死；无独立编号、无状态机；作废无任何回滚（不落账）。不进库存分录流水、不进收发货历史视图。
- **权限**：不新增权限资源码，随 `sales.delivery` 各动作（同发料清单随父单先例）；录入与查看入口均在发货单抽屉内。
- **界面**：发货单抽屉条目表下方加「装箱清单」编辑区，草稿可编辑、审核后只读；物料录入从本单发货条目的物料中带出筛选（草稿不硬卡，审核兜底）。不进列表 tab、不进 CSV 导出。
- **打印**：作为发货单 has_many（`pack_lines`）接入 meta，自动以 `${pack_lines.*}` 循环区进入打印字段目录；无专属打印开发。
- **术语**：子表＝**装箱清单**、行＝**装箱行**；「装箱单」仅为口语/打印件称呼，不是独立单据。词条已写入 CONTEXT.md。
- **模块落点**：Go 履约域销售发货侧（`fulfillment/standard`）扩展——行模型、快照冻结、审核校验全部纳入既有发货审核事务；meta 注册发货单的 `pack_lines` has_many（打印字段目录与前端网格元数据同源派生）；权限目录不加资源码。（Ash 侧为历史遗留，新功能不再落 Elixir。）

## Testing Decisions

- **唯一主接缝：Go 域服务层**——`fulfillment/standard` 的 Postgres 集成测试模式：真库 + `testutil` fixtures + 依赖注入桩（取号等），断言事实与校验报错（`apierror`）。Prior art：`server/internal/domain/fulfillment/standard/postgres_test.go` 的销售发货审核/作废/零金额跳总账/负库存回滚/容差/并发用例——装箱校验用例是其平移。
- HTTP 层仅在需要时补「鉴权先于解码」类契约用例（prior art：`server/internal/http/server_fulfillment_test.go`），不为装箱行新增 web 接缝。
- 好测试的标准：每个用例只断言「动作之后事实表变成什么／动作被拒绝并报什么错」，不测内部实现（私有函数、DTO 内部结构）；用例间不依赖执行顺序。
- 测试重点：
  - 单位折算：转换单位装箱行正确折 base 参与汇总比对。
  - 全有或全无各拒绝分支：漏装物料、装箱量少于/多于发货量、含发货外物料；报错点名物料。
  - 空表跳过校验、草稿保存不校验、审核后随单锁死不可改、随单级联删除。
  - 快照冻结：保存后改物料主数据不回溯。
  - 权限继承：无 `sales.delivery` 相应动作权限者不能读写装箱行（AuthzFixtures 先例）。
- 好测试的标准：每个用例只断言「动作之后事实表变成什么／动作被拒绝并报什么错」，不测内部实现。

## Out of Scope

- **箱级属性**（毛重/净重/尺寸）与两层「箱头＋箱内行」模型——将来纯加箱头表、行挂箱号演进，不推翻本期结构。
- **部分装箱**（⊆ 口径：只承诺没多装）——将来确有「散件不装箱但要出箱单」诉求时把 = 放宽，历史单照样合法。
- 装箱清单作为独立单据资源、独立编号与状态机；箱号主数据；按箱报表。
- 对销售对账、收发货历史、待办、库存/总账的任何联动。
