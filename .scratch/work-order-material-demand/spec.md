# Spec: 工单物料需求派生（嵌件/材料再分流）

**Status:** ready-for-human  
**Feature slug:** `work-order-material-demand`  
**Depends on:** 履约需求与生产执行（已交付）、履约安排混排与工单 BOM（已交付）、需求-采购串联（已交付）

## Problem Statement

车间主任按履约需求单开了生产工单、挂上 BOM 后，工单快照里虽然看得到嵌件和其他材料的配料明细，但这些材料需求**到此为止**——系统里没有任何机制把它们变成下游单据。车间只能对着快照手工誊抄：哪个嵌件下给哪个兄弟车间、哪些材料报给采购、仓库里有多少现货可以不用报，全靠人肉判断和线下沟通。誊抄既慢又错：漏报导致停工待料，重报导致材料翻倍，工单作废后已报出去的材料需求成了无源之水。同时「仓库里有现货的料不该再报需求」这条最朴素的常识，系统完全帮不上忙。

## Solution

在生产工单上提供「生成物料需求」动作：按工单的 BOM 快照展开配料，逐行显示毛需求（计损耗）、参考库存（本公司全部仓库现货合计快照）与默认净需求，车间逐行选定去向（某车间 / 采购 / 不需要）后一次提交，系统按去向分组自动生成多张履约需求单**草稿**——每个目标车间一张（头已填下发车间）、采购向一张（下发为空，留采购/委外勾选池消化）。车间在需求单界面改草稿、自行审核确认，下游车间与采购立即接力；子车间开工单后可再次派生，形成不限深度的多级展开。工单作废时自动清掉还没确认的派生草稿，已确认的只警告不拦截。

## User Stories

1. As a 车间主任, I want 在工单上一键展开 BOM 快照配料, so that 不用手工誊抄嵌件和材料清单
2. As a 车间主任, I want 每个配料行看到毛需求 = 净用量 ×(1+损耗率)× 工单数量, so that 报下去的量含损耗、下游不会长期欠料
3. As a 车间主任, I want 每个配料行看到本公司全部仓库的现货合计作参考库存, so that 知道哪些料不用报
4. As a 车间主任, I want 净需求默认 = 毛需求 − 参考库存且可手改, so that 现货抵扣自动化但我保留最终裁量
5. As a 车间主任, I want 参考库存只是生成瞬间的快照、不锁不扣, so that 不因系统预留而卡住别人的正常出入库
6. As a 车间主任, I want 逐行（可批量）选去向：某车间 / 采购 / 不需要, so that 一次动作完成全部分流
7. As a 车间主任, I want 参考库存足够的行默认标「不需要」, so that 有库存的料天然不进需求单
8. As a 车间主任, I want 提交后按去向自动拆成多张需求单草稿（每个目标车间一张、采购向一张）, so that 下发车间是头级字段的约束不用我手工拆单
9. As a 车间主任, I want 车间向草稿的头已填好下发车间, so that 兄弟车间确认后立即可见
10. As a 车间主任, I want 采购向草稿下发车间为空, so that 计划/采购走勾选池正常消化
11. As a 车间主任, I want 派生草稿的需求日默认 = 工单需求日且可改, so that 要提前备料时手改即可
12. As a 车间主任, I want 派生出来的是草稿、我可改可删后再审核, so that BOM 脏数据在确认前被拦住
13. As a 车间主任, I want 我对自己派生的需求单能改能审, so that 不用把单子推回计划多一次交接
14. As a 车间主任, I want 我仍然不能手工建需求单、不能勾选销售条目, so that 需求入口的职责边界不变
15. As a 车间主任, I want 我只能看到下发到本车间的需求单（含我派生的）, so that 数据范围规则对派生单一视同仁
16. As a 车间主任, I want 重复点「生成物料需求」且已有未删除派生草稿时被提示, so that 不会不知不觉把材料需求翻倍
17. As a 车间主任, I want 需求行上能看到来源工单链接, so that 这批材料是给哪张工单备的可追溯
18. As a 车间主任（子车间）, I want 收到派生需求单后能开自己的工单并继续向下派生, so that 多级 BOM 逐层展开
19. As a 车间主任, I want 作废工单时未确认的派生草稿被自动删除, so that 不留孤儿需求
20. As a 车间主任, I want 作废工单时若派生单已确认则收到警告但不拦截, so that 下游已执行的事实由人来收场而不是系统猜
21. As a 车间主任, I want 改工单数量不回溯已派生的草稿, so that 快照脱钩语义与 BOM 主数据先例一致
22. As a 计划员, I want 派生需求单在我的需求单列表里可见可查（含来源工单）, so that 全局需求仍尽收眼底
23. As a 计划员, I want 派生行不占用销售条目可占用量, so that 材料需求不会错误挤压销售口径
24. As a 采购员, I want 采购向派生草稿确认后进入既有勾选池, so that 下单流程零新增学习成本
25. As a 仓管/财务, I want 整个派生过程不写任何库存分录、不产生预留, so that 数量账口径不被污染
26. As a 审计员, I want 派生动作与派生单的创建都留审计痕, so that 材料需求的来龙去脉可查
27. As a 任何用户, I want 未挂 BOM 快照的工单点该动作得到明确报错, so that 知道要先选 BOM
28. As a 任何用户, I want 已完工/已作废工单不能执行该动作, so that 派生只发生在投产期内

## 差异点拆解（现状 → 目标）

按系统面逐条列出本次要动的点，每条标注「改 / 增 / 不变」：

1. **需求行来源建模（改）**：现状行上唯一来源字段是可空 `sales_order_item_id`；目标新增可空来源列 `source_work_order_id`（挂 `mfg_work_order`），与销售来源**互斥**（保存校验二选一或皆空），销售占用校验仅在有销售来源时触发，工单来源行天然不占。
2. **需求单创建入口（增）**：现状入口 = 手工建单 + 销售勾选纳入，均要求 `mfg.demand:create`；目标新增第三个入口——工单「生成物料需求」动作内的**受信任写**（服务内直接落头+行，不校验 `mfg.demand:create`），与「动作内系统写他域不另要码」先例（生产入库审核写库存分录）同构。
3. **权限矩阵（改）**：现状需求单全码在计划侧、车间零权限；目标车间角色获 `mfg.demand` 的 `read/update/confirm/delete`（**不授 `create`**，手工建单与勾选销售入口因此天然关闭），数据范围沿用「本部门=下发到本车间」的 assigned 形态；新增动作码 `mfg.work_order:generate_material_demand`（meta 声明即入权限目录）。
4. **库存余额的使用（增）**：现状库存引擎的 balance 聚合只在库存模块对外；目标制造域**只读复用**该引擎按「公司 + 物料、跨全部仓库合计」取参考库存，不新建表、不写分录、无预留概念。
5. **数量口径（增）**：现状无此概念；目标毛需求 = 快照配料行净用量 ×（1 + 损耗率，空按 1）× 工单 base 数量（即 BOM 文档既有「理论耗用」），净需求默认 = 毛 − 参考库存，行单位沿用配料行单位（限子物料默认/转换单位，复用既有单位校验），参考库存按同单位换算展示。
6. **去向分流与拆单（增）**：现状需求单头级单一下发车间、拆单靠人；目标派生提交时按去向分组——每个目标车间一张草稿（`assigned_dept_id` 已填）、采购向一张（空），同一张工单的派生在一张「来源批次」内完成（多张草稿共享来源工单，行级链接）。
7. **工单作废联动（改）**：现状作废只释放生产安排与投影；目标追加——级联物理删除该工单**未删除的派生草稿**（草稿本可物理删，无审计负担），存在**已确认**派生单时在响应里带警告名单但不拦截；工单删除动作同理。改数量**不回溯**（不变，明示确认）。
8. **需求行展示（增）**：现状需求行列表/抽屉只展示销售来源；目标展示来源工单号链接（只读穿透，受工单读权限与数据范围约束）。
9. **meta 声明（增）**：工单资源 `actions` 加 `generate_material_demand`（row 级）；需求行字段目录加来源工单列；权限目录自动收录新码（seal 期校验）。
10. **横切设施（不变为主）**：派生草稿照常走编号规则取号、照常写审计（动作在工单上留 `generate_material_demand` 痕、派生单留创建痕）；**待办不接**（需求单/工单现状即未接，本特性不新增）；打印模板不动。
11. **完成口径（不变，明示确认）**：父需求行完成只由生产入库回写，与子级派生链履行状态**零联动**；系统不建齐套概念。
12. **前端动作与弹窗（增）**：工单列表/抽屉加动作按钮（可见条件 = 进行中工单；无 BOM 快照配料行时服务端 422 明确报错）+ 分流弹窗（形态复刻销售勾选纳入需求单的 Modal+表格先例：逐行去向选择、毛需求/参考库存/净需求三列、净需求可编辑、批量设去向）；需求单前端无新手势，车间看到的建单按钮因无 `create` capability 自动隐藏。

## Implementation Decisions

- **动作落点**：生产工单资源新增 row 级自定义动作 `generate_material_demand`，权限码 `mfg.work_order:generate_material_demand`；路由 `POST /work-orders/:id/generate-material-demand`，guard 该单码（**不** allOf `mfg.demand:*`——这是「限定入口」的实现方式：车间角色只持工单动作码，需求单写库走服务内受信任写）。
- **请求/响应契约**：请求体 = 行数组，每行 `{ componentId（快照配料行）, qty（净需求，行单位）, target: { kind: 'dept', deptId } | { kind: 'purchase' } }`，未选中的配料行不出现即视为「不需要」；服务端逐项校验（快照行属于本工单、单位合法、dept 同公司未停用、qty > 0、数量上限 = 毛需求×(1+需求超安排比例)?——**不**，派生行尚无安排，超安排闸门在下游执行时才吃，此处只卡 qty > 0 与合理性上限=毛需求本身可改大由人负责，不设硬顶）。响应 = 生成的需求单草稿列表（id + 单号 + 去向），以及「已存在未删除派生草稿」的警告标记（前端二次确认后带 `force: true` 重发）。
- **拆单规则**：按 target 分组——`dept` 相同的车间合一张草稿（头 `assigned_dept_id=该车间`），`purchase` 合一张草稿（`assigned_dept_id=null`）；每张草稿头 company=工单公司、demand_date=动作当天、备注自动带来源工单号；行 need_date=工单 need_date、source_work_order_id=工单 id、qty=净需求、单位=快照配料行单位（服务端复算 base_qty 与物料/单位快照，不信任前端折算）。
- **参考库存取数**：库存引擎 balance 按 `{ companyId, materialId }`（不指定仓库）聚合后求合计，6 位精度，按配料行单位换算展示；取数时点 = 打开弹窗时（由独立查询端点或动作端点的 dry-run 模式提供，前端不自行聚合）。
- **草稿创建的内部实现**：不走需求单既有 `POST /demands` + 逐行 `/demand-items` 的公开端点（那会要求 create 码），服务内同事务落头+行；多张草稿一个事务，任一失败整体回滚。
- **车间需求单权限**：授予 `read/update/confirm/delete`、数据范围限本部门（assigned 形态既有机制）；`update/delete` 天然只对草稿生效（既有状态机约束），车间因此只能动「下发到本车间的草稿」——含自己派生的与计划下发途中的，接受此副作用（草稿是未生效意图）。
- **作废级联**：`voidWorkOrder`（及删除）在释放安排后追加——删除 `source_work_order_id=本工单` 且 status=draft 的需求单（连行级联）；存在 status=confirmed 的派生单时收集单号写入响应警告，不拦截。
- **多级递归**：零专设代码——派生单确认后，子车间按既有规则开工单，新工单同样带动作按钮，自然递归；深度不设限（BOM 成环由树展开视图检测先例兜底）。
- **动作可用条件**：工单 status=in_progress；无 BOM 快照配料行 → 422「工单未挂 BOM 快照，无法生成物料需求」。
- **审计**：工单上写 `generate_material_demand` 动作痕（含生成单号清单）；派生单头/行走既有创建审计；级联删除写删除审计。
- **编号**：每张派生草稿经编号规则取 `demand_no`（留空自动取号路径）。

## Testing Decisions

- **什么是好测试**：只测外部可观察行为（端点状态码、响应体、数据库里落的事实、权限拒绝），不测内部函数调用与实现细节；接缝从高往低选，能一个接缝覆盖的不拆两个。
- **接缝 1 · 服务层 PG 集成**（主接缝，复刻 `manufacturing.integration.test.ts` 风格：手工装配服务 + superAdmin actor + `SYNIE_TEST_DATABASE_URL` 门控）：覆盖派生逻辑全部细节——理论耗用公式（含损耗率空/非空）、参考库存快照参与净需求默认、按去向拆单分组（多车间+采购混合）、行单位沿用与 base 复算、来源互斥校验、作废级联删草稿、已确认派生单只警告、改数量不回溯、重复生成警告、无快照报错、多级递归（派生单→子工单→再派生）。
- **接缝 2 · 全栈 HTTP 权限**（复刻 `server/test/demand-dispatch.integration.test.ts` 的 `buildTestApp` 双角色模式）：车间角色持动作码可完成派生+对自己派生单 update/confirm/delete，但 `POST /demands` 手工建单 403、销售勾选相关端点 403、看不到未下发到本车间的需求单；计划角色行为不回归。
- **接缝 3 · meta 纯单测**（复刻 `manufacturing.meta.test.ts`，无 DB）：新动作声明与权限码入目录、需求行来源工单字段投影、seal 期校验通过。
- **接缝 4 · e2e 延伸**（在现有 `manufacturing.api.e2e.ts` 大用例末尾延伸，不另起套件）：弹窗逐行选去向提交 → 断言生成草稿数量与去向 → 需求单页面可见来源工单列。
- **数据准备与清场**：沿用现状——主数据裸插、业务单据走 API、每文件 randomUUID 后缀、`afterAll` 逆序 DELETE 清场（含审计/附件关联表）。
- **Prior art**：聚合草稿 wire 测试（stub-service Hono 模式）仅在请求体 wire 校验复杂时参照；本特性请求体简单，预期用不上。

## Out of Scope

- 库存预留/分配/锁库（参考库存是纯快照参考）。
- 齐套检查：工单开工、生产入库不检查子级材料需求履行状态；父需求行完成与子级链零联动。
- 按 BOM 快照实扣料、领料单、WIP 仓。
- 物料「默认来源（自制/外购）/默认车间」主数据与自动预分流。
- 提前期/lead time 计算（需求日默认=工单需求日，提前靠手改）。
- 待办接入（派生草稿提醒等）——需求单/工单现状未接待办，本特性不新增。
- 委外作为独立去向（委外消化走采购向草稿 + 既有委外勾选池）。
- BOM 树实体、多级一键全展开（递归靠各车间逐层动作驱动）。
- 派生草稿的批量关闭/批量删除工具。
- `docs/产品文档/` 正文更新随实施同步（ADR 已登记同步清单）。

## Further Notes

- 术语「物料需求派生（生成物料需求）」已入 `CONTEXT.md`，实现与文档统一用该词；界面按钮文案建议「生成物料需求」。
- 「车间可 update/confirm/delete 下发到本车间的草稿」是权限模型的刻意取舍：粒度再细（只能动自己派生的）需要发明「按来源区分授权」的新机制，违背最少接缝原则；若日后出现滥用再收。
- 派生行上的 arranged/completed 投影、需求超安排比例闸门、自动完成判定全部复用既有逻辑，本特性零改动——派生行确认后与手工行完全同构，这是设计刻意追求的效果。
- 请求体里的净需求由前端给出默认值（毛−参考库存），服务端**重算毛需求并校验单位/合法性**但不硬卡净≤毛（允许人改大），只在响应里回显服务端算出的毛需求供核对。
