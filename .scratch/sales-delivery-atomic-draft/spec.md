# 销售发货整单草稿原子保存规格

Status: resolved

## Problem Statement

销售发货抽屉当前把表头、发货条目、装箱箱和装箱清单拆成多次独立写请求。一次“保存”实际跨越多个数据库事务，前端还需要负责创建顺序、临时 ID 映射、差异计算、删除顺序和逐行失败汇总。

当中间任一请求失败时，数据库可能留下只有表头、缺少部分发货条目、只有装箱箱或只有部分装箱行的不完整草稿。用户看到的是一次保存动作，却无法获得整单成功或整单失败的保证。

“保存并审核”会在前端保存流程返回单据 ID 后继续发起审核；现有明细保存失败只被汇总而没有阻断整个提交流程，因此系统可能尝试审核一张只保存了部分内容的销售发货单。除数据一致性风险外，这套编排也让销售发货抽屉与多个细粒度写接口高度耦合，后续增加子表或校验时需要在浏览器继续扩展事务式业务逻辑。

## Solution

销售发货改为以整张草稿为写入边界。新建和编辑分别使用明确的整单创建、整单替换操作，但接收相同的完整嵌套草稿：销售发货单包含发货条目和装箱箱，每个装箱箱包含自己的装箱清单行。

后端在单一数据库事务中校验并持久化完整草稿。新建时，表头和全部子记录全部成功后才提交；替换时，后端根据完整快照计算子记录的新增、修改和删除，请求中缺失的既有子记录视为删除。任何表头、发货条目、装箱箱或装箱行失败都会回滚整次保存。

前端只负责维护用户正在编辑的完整草稿并提交一次请求，不再编排子记录写入。保存失败时保留抽屉内的全部输入，并通过带索引的字段路径把错误定位到对应字段或表格行。

“保存并审核”继续保持两个阶段：先原子保存完整草稿，再独立请求审核。审核失败不回滚已经成功保存的完整草稿，用户可以修正审核所提示的业务问题后再次审核。

## User Stories

1. 作为销售内勤，我希望一次保存整张销售发货草稿，以便我看到的一个保存动作对应数据库中的一个原子结果。
2. 作为销售内勤，我希望新建销售发货单时表头和全部发货条目一起提交，以免留下只有表头的空壳单据。
3. 作为仓管，我希望装箱箱和所属装箱行一起保存，以免出现空箱或装箱行丢失。
4. 作为仓管，我希望一只装箱箱直接包含自己的装箱行，以便系统不需要我理解临时箱 ID 与数据库 ID 的转换。
5. 作为销售内勤，我希望已有发货条目、装箱箱和装箱行在草稿中保留稳定身份，以便编辑后仍能识别原记录。
6. 作为销售内勤，我希望新增的发货条目、装箱箱和装箱行无需预先取得数据库 ID，以便新建整单只需要一次提交。
7. 作为销售内勤，我希望编辑已有草稿时提交保存后的完整状态，以便无需在浏览器中维护一组增删改命令。
8. 作为销售内勤，我希望从草稿中移除的既有发货条目在保存后被删除，以便界面内容与数据库内容一致。
9. 作为仓管，我希望从草稿中移除的装箱箱及其装箱行在保存后一起删除，以便装箱事实不会残留孤儿记录。
10. 作为仓管，我希望可以在同一次保存中新增箱、修改既有装箱行并删除另一只箱，以便复杂编辑仍只有一个成功或失败结果。
11. 作为销售内勤，我希望表头和子记录的任一校验失败都会回滚整单，以便我不会误以为部分数据已经安全保存。
12. 作为销售内勤，我希望保存失败后抽屉保持打开并保留全部未保存输入，以便我可以直接修正问题。
13. 作为销售内勤，我希望错误能定位到具体发货条目字段，以便我不必逐行猜测哪一项有问题。
14. 作为仓管，我希望错误能定位到具体装箱箱或装箱行字段，以便复杂箱单也能快速修正。
15. 作为销售内勤，我希望保存失败时只看到整单失败提示，不出现“部分成功”消息，以便反馈与真实事务结果一致。
16. 作为销售内勤，我希望未知的子记录 ID 被拒绝，以免错误请求静默创建或覆盖意外记录。
17. 作为公司数据管理员，我希望跨销售发货单复用子记录 ID 的请求被拒绝，以免一张单据篡改另一张单据的数据。
18. 作为销售内勤，我希望同一子记录 ID 在一个草稿中重复出现时整单被拒绝，以免后端猜测哪一份内容有效。
19. 作为销售内勤，我希望只能替换仍处于草稿状态的销售发货单，以便已审核单据继续保持锁定。
20. 作为权限管理员，我希望整单创建仍受销售发货创建权限控制，以便权限模型不因接口聚合而放宽。
21. 作为权限管理员，我希望整单替换仍受销售发货修改权限控制，以便子记录变化被视为父单草稿修改的一部分。
22. 作为只读用户，我希望仍能查询销售发货条目、装箱箱和装箱行，以便列表、对账和查看功能不受写接口收缩影响。
23. 作为销售内勤，我希望“保存并审核”先确认完整草稿保存成功，再发起审核，以免审核部分保存的单据。
24. 作为销售内勤，我希望审核失败时完整草稿仍然存在，以便审核业务校验失败不会抹掉合法录入。
25. 作为销售内勤，我希望审核失败后可以修改草稿并再次保存审核，以便纠错流程不中断。
26. 作为审计人员，我希望本次架构调整不伪造新的业务审核事件，以便操作日志语义保持稳定。
27. 作为审计人员，我希望既有表头创建、表头修改和发货条目创建日志继续产生，以便已有追踪能力不退化。
28. 作为系统维护者，我希望销售发货抽屉不再直接调用发货条目、装箱箱和装箱行的独立写接口，以便事务规则集中在后端模块。
29. 作为系统维护者，我希望整单创建与整单替换复用同一个事务协调边界，以便新增子表或校验时只扩展一个深模块。
30. 作为系统维护者，我希望旧的子记录写入口在迁移完成后被删除，以便系统只有一个权威写路径。
31. 作为系统维护者，我希望新接口返回持久化后的权威草稿，以便前端获得数据库生成的记录 ID、箱号和派生字段。
32. 作为并发编辑者，我希望本次调整保持现有最后保存者覆盖语义，以便架构修复不会暗中引入新的版本冲突规则。
33. 作为产品负责人，我希望销售发货以外的单据不在本次改造中变化，以便可以先验证一个清晰的纵向切片。

## Implementation Decisions

- 本规格只改造销售发货单，不建立跨单据的通用“文档保存框架”，也不同时迁移采购入库或其他业务单据。
- 写模型以销售发货单为聚合边界：完整草稿包含表头字段、发货条目集合、装箱箱集合，以及嵌套在各装箱箱下的装箱清单行集合。
- 已持久化的子记录携带 ID；新子记录不携带 ID。请求不使用前端临时 ID 表达数据库归属。
- 对外提供两个明确操作：创建完整草稿和替换指定的既有草稿。两者使用同一草稿结构并复用同一事务协调器，不使用会猜测创建或更新语义的 upsert。
- 创建完整草稿只接受不含销售发货单 ID 的输入。表头、全部发货条目、装箱箱与装箱行必须在同一事务中成功，失败时不得留下任何部分记录或操作日志。
- 替换完整草稿由路径中的销售发货单 ID 确定目标。请求中出现的既有子记录 ID 必须属于该单据；未知、跨单和同请求重复的 ID 都是整单校验错误。
- 替换采用完整快照语义：请求中存在的子记录代表保存后的完整状态；数据库中存在但请求中缺失的发货条目、装箱箱或装箱行视为删除。
- 装箱箱是嵌套边界。后端先建立请求中的箱与其装箱行归属，不要求前端创建箱后再把数据库 ID 回填到装箱行。
- 单次替换必须锁定目标草稿并确认仍可编辑，随后在同一事务内完成表头校验、引用校验、子记录差异计算、写入、附件同步和日志写入。
- 整单创建要求销售发货创建权限；整单替换要求销售发货修改权限。快照中删除子记录属于父单修改，不额外要求用户取得父单删除权限。删除整张销售发货单的既有权限和行为不变。
- 领域校验继续复用现有销售发货规则，包括公司数据范围、对手、订单条目、单位、仓库、科目、物料快照和草稿状态约束；本规格不改变审核时的超发、装箱全有或全无、库存或总账规则。
- 校验错误沿用统一 API 错误包络，并使用可索引的字段路径定位到草稿中的字段。路径至少能区分表头、某个发货条目、某个装箱箱和箱内某个装箱行。
- 前端提交失败时不得清空本地草稿、关闭抽屉、刷新为部分服务器状态或显示部分成功提示；可定位的错误优先标在对应字段或表格行，同时保留汇总提示。
- 整单写操作返回持久化后的权威草稿，包括数据库生成的 ID、系统生成的箱号以及既有派生和快照字段，使前端能用一次响应同步本地状态与查询缓存。
- “保存并审核”保持顺序式两请求：整单保存成功后才调用既有审核操作。审核失败不会回滚完整草稿，也不会把保存与审核合并成一个数据库事务。
- 本次不增加修订号、更新时间条件或乐观锁。每个保存事务内部保证一致性，多个用户先后保存时保持最后保存者覆盖。
- 操作日志保持当前业务语义：表头创建和有效修改继续记录，新增发货条目继续记录；本次不新增整单嵌套差异日志，也不把保存记录为审核事件。
- 销售发货抽屉迁移后，删除发货条目、装箱箱和装箱行的独立创建、修改、删除接口及其前端写调用，只保留这些资源的查询和单条读取能力。
- 销售发货整单删除、审核、作废、查询和读取行为不因本规格改变。
- 不需要数据库结构迁移；改动集中在事务编排、HTTP 契约、前端资源访问和抽屉提交流程。
- 产品文档必须说明整单原子保存、完整快照删除语义和保存并审核的两阶段行为。领域词汇沿用“销售发货单”“发货条目”“装箱箱”“装箱清单（行）”，不新增根领域词条。

## Testing Decisions

- 好测试只断言外部可见行为：HTTP 响应、统一错误字段、数据库最终事实、浏览器发出的请求和用户可见状态；不断言私有函数、SQL 执行顺序、内部差异集合或 React state 实现。
- 主验收接缝是销售发货整单 HTTP 接口连接真实 PostgreSQL。通过真实认证与路由进入业务服务，覆盖请求结构、权限、事务、错误包络和数据库结果。
- 主接缝优先沿用现有履约 API 端到端测试的真实应用与数据库夹具模式；事务细节可沿用既有履约 PostgreSQL 集成测试作为更快的回归先例，但不重复断言同一实现细节。
- 薄 UI 接缝使用现有浏览器端到端测试设施，验证新建和编辑抽屉各只发一次整单保存请求，并验证保存并审核产生“整单保存 → 审核”的两次顺序请求。
- 创建测试至少覆盖：完整嵌套草稿成功、数据库生成 ID 与箱号返回、发货条目或装箱行失败时表头与其他子记录全部不存在、失败事务不残留操作日志。
- 替换测试至少覆盖：同一请求同时新增/修改/删除子记录、删除箱级联清理其装箱行、保留未变记录、空集合清空对应子表、事务失败后整单保持保存前状态。
- 身份安全测试至少覆盖：未知子记录 ID、跨销售发货单 ID、重复发货条目 ID、重复装箱箱 ID和重复装箱行 ID，均返回校验错误且不改变任一单据。
- 状态和权限测试至少覆盖：已审核单不可替换、无创建权限不可整单创建、无修改权限不可整单替换、只读查询接口继续可用。
- 错误定位测试至少覆盖表头字段、发货条目字段和嵌套装箱行字段，确认统一错误包络包含稳定的索引路径。
- UI 失败测试验证抽屉仍打开、用户输入未丢失、无部分成功提示，并能在对应区域看到错误反馈。
- 保存并审核测试覆盖：保存失败时不发审核请求；保存成功才发审核请求；审核失败时数据库保留刚保存的完整草稿，并允许用户继续编辑。
- 契约收缩测试验证前端不再引用子资源独立写操作，服务端对应写路由不可访问，而子资源查询和读取仍可访问。

## Out of Scope

- 采购入库、委外发料、委外入库、销售订单或其他单据的整单保存迁移。
- 一个适用于所有业务单据的通用文档聚合框架。
- 乐观锁、修订号、冲突比较界面或多人协同编辑。
- 将保存和审核合并为一个请求或一个数据库事务。
- 新的整单差异审计日志、子记录修改日志或装箱变更日志模型。
- 改变销售发货审核、作废、库存分录、总账分录、已发数量或已对账数量规则。
- 改变装箱箱重量、装箱行净重、装箱全有或全无校验或打印字段目录。
- 数据库表、外键、索引或持久化字段调整。
- 前端通用数据网格、通用抽屉或资源客户端体系的全面重构。
- 为旧细粒度写接口提供兼容层、双写期或第三方调用迁移窗口；系统尚未上线，迁移完成即收缩旧写面。

## Further Notes

- 该工作是架构深化的第一个纵向切片，目标是把浏览器中的事务式业务编排下沉到销售发货深模块，而不是新增业务能力。
- 实施顺序采用扩展—迁移—收缩：先让整单创建可用，再实现整单替换和失败闭环，最后删除旧的子记录写面。每一步都应保持可验证，最终只保留一个权威草稿写边界。
- 现有“装箱可先于发货条目录入”“装箱清单可为空”“有装箱时审核全有或全无”等领域语义全部保留。
- 根领域词汇表已经定义本规格涉及的全部业务术语；实现交付时只需核对一致性，不应把“完整草稿快照”之类的技术表达提升为业务词条。
