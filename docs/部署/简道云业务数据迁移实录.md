## 4. 超发容差（D5）技术说明

| 路径 | 上限 |
|---|---|
| API `PATCH /settings/supply-chain` | **0～1**（100%） |
| 表 `sal_setting` CHECK | 原 `<= 1` |
| **迁移临时（SQL）** | drop CHECK 后写入 **1000**（即 100000%） |

恢复模板（迁完执行）：

```sql
UPDATE sal_setting SET
  delivery_overship_ratio = 0,
  receipt_overreceive_ratio = 0,
  updated_at = (now() AT TIME ZONE 'utc');
ALTER TABLE sal_setting ADD CONSTRAINT delivery_overship_ratio_range
  CHECK (delivery_overship_ratio >= 0 AND delivery_overship_ratio <= 1);
ALTER TABLE sal_setting ADD CONSTRAINT receipt_overreceive_ratio_range
  CHECK (receipt_overreceive_ratio >= 0 AND receipt_overreceive_ratio <= 1);
```

（若业务要保留 100% 过渡，可改为 `= 1` 再加 CHECK。）

## 8. 坑（本轮）

1. API 超发比例硬限 0～1，与「临时放很大」冲突 → 必须 **SQL 改库 + drop CHECK**，不能只调 API。
2. **扩容订单 = 虚假数据**，已整批物理删除；后续禁止。
3. 客户物料一料一客：跨客户发货无法仅靠超发解决。
4. 发货 void 后列表 count 含 voided 行；垃圾单应物理删掉，不要留作废痕污染期初。
5. 第二家公司不能凭简称「东方」脑补成「东方电气」——票面法定名称是 **玉环县东方钢板网厂**。
6. 发票若走审核过账会和期初凭证双计应收；期初发票只进台账、不过账。
7. 简道云订单条目 `_widget_1745818019983`=**未发**、`9984`=**已发**；载荷用反后把已发完的单当成在途导入。真未发口径是「需要发货 ∧ 未发>0」（约 200 行，与未发货清单一致）。
8. 对账必须有出库单据：只改 `shipped_qty` / 关闭订单不够；历史出库要进发货单，已结清部分不过账。
9. 农行代发有时把户名写成「浙江省」、人名落在摘要里（2024-05-10/13）；流水要改回户名再对账，见 §17。

## 12. 2026-08-14 收干净销售链拆行残留

承接 §11。FIFO 导入把一行简道云出库拆到多张订单；UUID 改挂只动了能对上的那一片，碎片仍挂在更晚的真订单上（把别的单的已发抬高）。本轮只 SQL 改挂 / 重算 `shipped_qty`：不改订购 `qty`、不过账、不删真实出库事实、不新建扩容单、不动 `W(SO)-` / `XSFH`。

**超发是业务常态**（产品交货本来就会超订购数量），不是迁移错误。本轮要拿掉的是挂错单的拆行碎片；挂对之后 `shipped_qty > qty` 应保留，不要再为「收到 0 条超发」去改挂或扩容。

### 算法

对 `remarks` 以 `简道云出库:销-` 开头的发货单：

1. 应有行 = 旧应用出库行（没有旧单则用新应用 `ship_items`）。
2. 实有行 = 线上 `sal_delivery_item`。
3. 主行 = 已按 UUID 挂在目标订单、且物料/图号（或名称规格）对得上应有行的（数量相等优先，拆片覆盖次之）。
4. 对不上的 = 碎片；`reconciled_qty=returned_qty=0` 才能动。
5. 碎片处理：
   - 该应有行有 UUID 目标且尚未盖满 → 补挂回目标订单行（§11 漏网，不是新建订单）。

6. 全量 `shipped_qty = Σ` 仍挂在该行上的发货数量；没有任何发货的置 0。
