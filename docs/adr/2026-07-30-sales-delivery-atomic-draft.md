# ADR：销售发货以整单草稿作为唯一写边界

销售发货原先由浏览器依次保存表头、发货条目、装箱箱和装箱行。用户执行一次保存，系统却跨越多个数据库事务；中途失败可能留下空壳单据或不完整子表，浏览器还必须维护临时箱映射、差异计算和删除顺序。

## 决策

- **聚合边界限定为销售发货单**：完整草稿由表头、发货条目、装箱箱和箱内装箱行组成。本次不抽象跨单据的通用文档框架，也不迁移采购入库等其他单据。
- **创建与替换是两个明确操作**：创建不接收已持久化子记录身份；替换由路径确定目标，并接收保存后的完整快照。两者使用相同的嵌套草稿结构。
- **一次保存只使用一个数据库事务**：表头、全部子记录、图纸挂接和既有操作日志共同提交或共同回滚。替换先锁定草稿，拒绝未知、跨单或重复的子记录身份；数据库中存在但快照中缺失的子记录视为删除。
- **后端返回权威完整草稿**：响应包含系统生成的记录身份、箱号、物料与订单快照及派生字段，浏览器不再逐项补写或推测服务端状态。
- **收缩销售子资源写面**：发货条目、装箱箱、装箱行仅保留查询和单条读取；独立创建、修改、删除入口移除。采购入库的子资源写入口不受影响。
- **保存与审核仍是两个阶段**：完整草稿保存成功后才可请求审核；审核失败不回滚已保存草稿。保存不是审核事件，不新增整单差异日志。
- **保持最后保存者覆盖**：本次不引入修订号、条件更新时间或乐观锁。每次保存自身保持一致，后提交的完整快照覆盖先提交结果。

## 否决方案

- **浏览器补偿或失败后重试剩余子记录**：无法给用户整单成功或整单失败的保证，且继续把事务规则泄漏到界面。
- **保留细粒度写入口并让聚合接口内部逐个调用 HTTP**：仍跨事务，也形成两个权威写路径。
- **保存与审核合并为一个事务**：审核可能因库存、超发或总账规则失败；这不应抹掉已经合法录入的完整草稿。
- **同步建设所有业务单据的通用聚合框架**：当前只有销售发货的装箱嵌套已证明需要该边界，提前泛化会扩大风险。

## 后果

- 销售发货前端必须维护并提交完整草稿，提交前必须确认全部子记录已经加载。
- 校验错误需要稳定的表头、条目、箱和箱内行索引路径，供抽屉就近展示。
- 旧销售子资源写调用立即失效；系统尚未上线，不提供兼容或双写窗口。
- 不需要数据库结构迁移，现有审核、作废、库存、总账和对账规则保持不变。
