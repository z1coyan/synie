# ADR：待办设施——轻量状态驱动提醒，不引入流程引擎

2026-07-25，拷问访谈定案（grill-with-docs）。

- **触发时点=客户已确认**：开票待办在常规销售对账单翻入「客户已确认」时产生；已结单时点才提醒是事后回声（票已开完），无行动价值。撤回确认/发票作废红冲退回确认态属于「同一提醒窗口的消失与复活」，由待办设施按状态推导，不做独立事件。
- **收件人=权限圈人**：对「可见该公司 + 持发票创建权限」的全部用户可见，任一人开出关联发票即全体消失。拒绝按角色圈人（角色是部署侧自由文本，无系统级「财务角色」可钉）与显式指派（多一步动作、经办人单点、确认人不天然知道票归谁开）。
- **待办≠流程**：系统不引入流程引擎/BPMN 式审批链。待办只解决「状态已变、谁该知道并去动手」的可见性问题；「单据该不该往下走」的控制力已由各单据硬编码状态机 + 工作流动作承载（对账单的客户确认闸门、发票关联校验即先例）。待办设施与状态机正交：状态机照旧写死在代码里，待办是从状态推导出的只读提醒，不反向驱动状态。
- **待办是派生物，不是单据**：待办不落独立生命周期（无指派人、无截止时间、无优先级、无催办），随源状态自动出现/消失，用户侧只有「已读/忽略」级别的个人痕迹。将来若真出现审批流需求（如超金额发货需经理批），审批节点是待办的**生产者之一**，本设施照常复用，届时另议。
