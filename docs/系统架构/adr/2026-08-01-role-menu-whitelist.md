# ADR：角色菜单白名单（菜单权限）

2026-08-01。

- **背景**：菜单一直是前端纯静态配置，所有登录用户看到全量菜单（54 项），与角色、权限完全解耦——「看不看得到入口」没有配置面，受限角色用户导航噪音大，「点进去没权限被拦」的割裂体验常态。规格原见 `.scratch/menu-permission/spec.md`（已删除，见 git 历史；grill-with-docs 十问定案）。
- **决策**：为角色增加**菜单白名单**——纯导航呈现层配置，与权限码体系正交：
  1. **语义**：菜单权限 = 菜单可见性，只管导航入口；**不是**数据行级权限（「行级权限」一词保留给将来的记录级数据范围）。
  2. **模型**：白名单 + **空集不启用**——角色存「可见菜单集合」，无任何行 = 未启用限制 = 维持现状全可见；「限制成什么都不可见」的状态不存在。
  3. **叠加**：多角色取白名单**并集**；仅当所有角色均无白名单行时不限制。加角色只加菜单，限制不因挂到未配置角色而意外失效；停用角色不参与并集（与权限码取数口径一致）。
  4. **粒度**：只配**叶子菜单项**；组/模块无独立 code，可见性由子项派生（有可见子项则父可见，勾光即消失），不写组/模块级通配（对齐「界面不写通配授权」惯例）。
  5. **边界**：菜单隐藏**不拦 URL 直达**；访问控制的唯一权威仍是权限码（页内门控 + API fail-closed），不做路由级第二道闸。
  6. **存储**：独立表 `sys_role_menu(role_id, menu_code)`（形态对齐 `sys_role_permission`）+ 独立 sync 端点 `GET/PUT /system/roles/:id/menus`；**不复用权限码体系**——权限码是「操作能力」，菜单可见性不是操作能力，不进权限目录、不污染权限码命名空间。`/auth/me` 增挂 `menuCodes`（空数组 = 不限制），超管恒空（对齐旁路先例）。
  7. **菜单 code**：每叶子项一个稳定 code（约定 `menu.<模块>.<路径末段>`），发布后**不可改**（改名 = 删旧 + 增新）；事实源仍是前端静态菜单声明，后端维护同构菜单目录仅供 sync 校验与已失效项判定，两侧由契约测试对拍防漂移。
  8. **内置角色**：对齐 builtin 先例——白名单只读、初始化种子写入：`admin` 恒空；`sales` 种子销售链菜单（`SALES_ROLE_MENUS`，与 `SALES_ROLE_PERMISSIONS` 对应）。迁移只建表不写行，老环境内置角色维持全可见（「内置角色只随初始化出现，老环境不强塞」）。
  9. **演进**：sync 写入校验拒绝目录外 code（逐个点名）；菜单项删除/改名后的孤儿行**保留不自动删**，配置界面提示「已失效 N 项」+ 一键清理；新增菜单项对已限制角色默认不可见（安全方向），管理员显式补勾才开放。
  10. **管理权限**：配置行为由新权限资源 `sys.role_menu`（read/update）门控，与 `sys.role_permission` 分离，「配功能权限」与「配菜单」可分人管理。
- **理由**：呈现层与访问控制职责单一、互不伪装（菜单不是安全边界，权限码也不背导航整洁）；空集不启用让存量角色零迁移零感知；并集单调可预期；独立表守住权限码语义边界，代价（后端菜单目录 + 契约测试）由 CI 兜住漂移。
- **不变量**：权限码体系（目录派生、通配仅种子可写、页内与 API 判定）完全不受本特性影响；菜单过滤失败 fail-open 于呈现（加载中全显），不影响任何写路径安全。
- **影响面**：新表 + 两个端点 + `/auth/me` 增字段（wire 兼容，纯增量）；前端菜单声明补 code、外壳统一走过滤派生；角色页加「配置菜单」入口。老环境升级即得能力、行为不变（所有角色未配置 = 全可见）。

> **2026-08-02 补充**：配置入口随后合并为角色行内单入口「权限与菜单」统一抽屉（菜单可见性区 + 功能权限区强隔离，合并仅容器层，本 ADR 全部不变量不受影响；规格原见 `.scratch/role-access-drawer/spec.md`，已删除）。
